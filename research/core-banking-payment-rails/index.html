1. Context of the Problem (2015-2019)

Between 2015 and 2019, the financial sector underwent major regulatory and structural modernizations in Europe, such as the introduction of the Payment Services Directive (PSD2) and the UK Open Banking framework. These regulations demanded near-instantaneous transaction validation, continuous auditability, and sub-50ms latency. In core transactional systems, the greatest architectural risk is the introduction of data race conditions (such as double-spending) under concurrent execution, resulting in ledger reconciliation drift where the balance sheet fails to balance.

2. Evaluation of Available Options

To achieve high transactional reliability under peak concurrency, three primary processing models were evaluated:

Architectural Pattern Pros Cons Suitable Use Case
Option A: SQL UPDATE Mutations Simple schema; direct data mutations; easy query logic. Relentless write contention; frequent row deadlocks; lacks transaction event trail. Low-concurrency, non-critical database applications.
Option B: Distributed Ledgers (Blockchain) Cryptographically secure, multi-party immutability; decentralized trust. Severe transaction latency (seconds/minutes); low throughput; lack of transaction finality. Inter-bank settlement rails with no real-time speed requirements.
Option C: Event Sourced Ledger + Distributed Pre-Locks (PostgreSQL + Redis) Immutable data audit trail; sub-50ms finality; zero database write contention. Requires complex CQRS query synchronization and event model handling. High-scale, real-time clearing rails. Chosen Option.

3. Architectural Selection Rationale

Option C was selected. Option A (direct relational database mutations) was rejected because modifying mutable balances directly in a table database is highly vulnerable to deadlock blocks and race conditions under concurrent spikes. It also fails strict auditing compliance by hiding the historical states of transaction changes. Option B (Blockchain) was rejected because, during the 2015-2019 era, DLT systems lacked the performance capabilities to meet transactional SLAs, often requiring minutes to guarantee cryptographic finality.

By implementing Option C, the core ledger model is built on strictly append-only principles in PostgreSQL. Account balances are never altered with SQL UPDATE commands; instead, balances are dynamically computed by summing a historical log of immutable debit and credit event records. A Redis distributed locking layer acted as an early-flow idempotency guard, rapidly rejecting duplicate transaction keys in-memory. This fast-fail mechanism protected the database connection pools from exhaustion, while PostgreSQL SELECT ... FOR UPDATE row-level locks provided the absolute, authoritative consistency boundary, with the zero-sum ledger invariant enforced firmly by the application's transaction model.

4. Stress-Testing, Chaos Injection & Telemetry

The transaction clearing prototype was validated by flooding the payment API with a throughput of 15,000 payment deposit and withdrawal events per second, representing a simulated transaction volume of £50M+ per day. To test robustness under failure states, active connection pools were saturated, and dockerized Go container nodes were randomly restarted mid-commit. The telemetry recorded:

  • Reconciliation Correctness: Zero balance sheet drift (0.00% ledger drift) was maintained across all test runs. PostgreSQL ACID transactional rollbacks cleanly isolated all aborted database sessions during container crashes.
  • Lock Performance: The Redis-based distributed pre-locking layer successfully deflected 94% of duplicate lock requests before they hit the database, preventing row lock contention and maintaining an average commit latency of just 18ms under concurrent load.
  • SLA Compliance: The payment rail completed transactions end-to-end within an average 18ms SLA, easily exceeding the strict sub-50ms target required for real-time payments.

5. Limitations

While the proposed architecture performs exceptionally well under the tested conditions, several operational limitations should be noted:

  • Redlock Clock Dependency: The distributed pre-locking layer relies on the Redlock algorithm, which assumes synchronized system clocks across the Redis cluster. Significant clock drift between nodes can violate mutual exclusion guarantees, requiring strict NTP/PTP monitoring.
  • Single-Primary Lock Bottleneck: Under extremely high transaction volumes focused on a small subset of hot accounts, the Redis instance handles all lock coordination, creating a potential processing bottleneck.
  • Eventual Consistency of CQRS Reads: Because balance history is computed dynamically or via projections, read-only queries might experience a minor sync delay compared to the write-side double-entry ledger.

6. Architectural Conclusions

The experiment demonstrates that mutable state is a primary risk to data correctness in core transactional systems under high concurrency. Designing ledgers as append-only event streams significantly improves financial audibility. By offloading transaction synchronization to an in-memory locking store like Redis, write contention is minimized, showing that high-throughput payment rails can achieve enterprise-scale performance while maintaining consistency under the simulated conditions.
